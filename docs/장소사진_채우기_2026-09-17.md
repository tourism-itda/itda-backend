# 장소 사진 채우기 + 카카오 후보 확정 버그 — 2026-09-17

> `API_변경사항_프론트전달_2026-09-17.md` 의 후속입니다. **프론트가 고쳐야 할 것 한 가지**(2장)와
> **백엔드에서 돌려야 할 배치**(4장)가 있습니다.

## 0. 세 줄 요약

- **카카오에서 온 식당·카페는 지금까지 루트에 담기지 못했습니다.** 고르면 "관광API 에서 장소를
  찾을 수 없습니다" 가 떴습니다. 확정 경로가 관광API 하나뿐이었기 때문입니다. 고쳤습니다.
- **장소 사진이 전부 비어 있던 원인**은 `place_image` 테이블에 **쓰는 코드가 아예 없었기** 때문입니다.
  관광API 가 `firstimage` 를 주고 있었는데 임포트 시점에 그냥 버리고 있었습니다.
- 프론트는 `POST /api/places/import` 요청에 **`source`·`name`·`latitude`·`longitude` 를 추가로 실어야**
  카카오 후보가 저장됩니다.

---

## 1. 무슨 일이 있었나

### 1-1. 카카오 후보가 루트에 못 들어간 이유

식당·카페 후보는 두 군데서 옵니다 (`CandidateFinder`).

1. 관광API `locationBasedList2` 를 먼저 채우고,
2. `candidate_limit` 에 모자라면 카카오 로컬(FD6/CE7)로 보충합니다.

그런데 확정 엔드포인트(`POST /api/places/import`)는 **무조건 관광API `detailCommon2` 에
contentId 로 조회**했습니다. 카카오 place id 는 관광API 의 contentId 가 아니므로 조회될 리가
없고, 그래서 카카오 후보는 **고르는 족족 404** 였습니다.

사진 유무와 상관이 있어 보였던 건 우연이 아닙니다 — **카카오 로컬 API 응답에는 이미지 필드가
아예 없습니다.** 실제 응답 필드는 이게 전부입니다:

```
address_name, category_group_code, category_group_name, category_name,
distance, id, phone, place_name, place_url, road_address_name, x, y
```

그래서 "사진 없는 카드 = 카카오 후보 = 반드시 실패" 였습니다.

### 1-2. 장소 사진이 비어 있던 이유

루트 응답의 `image_url` 은 `place_image` 의 `is_primary` 행에서만 옵니다
(`RoutePlanner.primaryImages`). 그런데 그 테이블에 **INSERT 하는 코드가 프로젝트 전체에
하나도 없었습니다.** 적재 SQL(`scripts/load-anchors-*.sql`)도 `place` 와 `content_place` 만
만들고 `place_image` 는 건드리지 않습니다.

관광API 는 `firstimage` / `firstimage2` 를 이미 내려주고 있었고 `TourApiPlace` 에 담기까지
했는데, `TourApiPlaceImporter` 가 `Place` 를 만들 때 그 값을 쓰지 않고 버렸습니다.

## 2. 프론트가 고쳐야 할 것 — `POST /api/places/import`

후보 목록(`CandidateView`)에 나간 값을 **그대로 더 실어 보내면 됩니다.**

```jsonc
// 전 (지금 보내고 있는 것)
{
  "external_id": "2869760",
  "place_type": "RESTAURANT"
}

// 후
{
  "external_id": "8260657",
  "place_type": "RESTAURANT",
  "source": "KAKAO",          // 신규 — CandidateView.source 를 그대로
  "name": "동북교자관 본점",     // 신규 — CandidateView.name 을 그대로
  "latitude": 37.28851,       // 신규 — CandidateView.latitude
  "longitude": 127.01238      // 신규 — CandidateView.longitude
}
```

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `source` | 아니오 | `TOUR_API` / `KAKAO`. **생략하면 `TOUR_API` 로 봅니다** — 기존 요청이 그대로 동작합니다 |
| `name` | `KAKAO` 일 때 | 카카오 검증용 상호 |
| `latitude` / `longitude` | `KAKAO` 일 때 | 카카오 검증용 좌표 |

`source: "TOUR_API"` 인 후보는 지금 보내던 그대로 두어도 됩니다. **`KAKAO` 후보만** 세 필드를
더 채워 주세요. `name` 과 좌표가 **둘 다 없으면** 400 이 납니다.

> **왜 이름·좌표를 받나요?** 저장에는 쓰지 않습니다. 카카오 로컬 API 에는 id 단건 조회가 없어서,
> 받은 이름·좌표로 **검색한 뒤 id 가 일치하는 결과만** 채택합니다. 저장되는 값은 전부 카카오가
> 돌려준 것이라, 클라이언트가 값을 꾸며도 임의의 place 를 밀어 넣을 수 없습니다.

### 응답 변화

응답의 `image_url` 이 **이제 실제로 채워집니다.** 예전에는 무조건 `null` 이라 확정 직후
카드에서 사진이 사라졌습니다.

## 3. 사진이 채워지는 순서

장소를 저장하는 모든 경로가 같은 순서를 따릅니다.

1. **관광API `firstimage`** — `source=TOUR_API` 인 장소. 가장 믿을 만합니다.
2. **좌표+이름 매칭** — contentId 가 없는 장소(카카오·시드 출처). 좌표로 주변을 훑고
   이름 유사도로 고릅니다.
3. **네이버 이미지 검색** — 위 둘이 실패했을 때. 제목에 상호가 들어간 결과만 채택합니다.

실측 커버리지 (시드 앵커 기준):

| 경로 | 결과 |
| --- | --- |
| 관광API contentId → `firstimage` | **16 / 18** |
| 좌표+이름 매칭 (contentId 없는 앵커) | 3 / 9 |
| 카카오 식당을 관광API 로 역매칭 | **0 / 15** — 관광API 에 아예 없는 가게들입니다 |

> 마지막 줄이 네이버 키가 필요한 이유입니다. 카카오로 보충한 식당·카페는 **네이버 말고는
> 사진을 구할 데가 없습니다.**

### 왜 좌표와 이름을 둘 다 보나

한쪽만 보면 둘 다 틀립니다. 실측 예:

| 방식 | 결과 |
| --- | --- |
| 이름만 (`searchKeyword2`) | 우리가 `거제포로수용소`, 관광API 가 `거제도 포로수용소` → **0건** |
| 좌표만 | `학도의용군 전승기념관` 에 근처 **죽림사** 사진, `5.18기념공원` 에 **광주일신여상** 사진 |
| 좌표 + 이름 유사도 | `거제도 포로수용소 유적공원` 채택(유사도 0.75), `포로수용소유적박물관` 거부(0.462) |

유사도는 글자 2-gram 자카드이고 임계값은 0.6 입니다 (`PlaceNameSimilarity`).
실측값을 `PlaceNameSimilarityTest` 에 그대로 박아 뒀으니 임계값을 건드리면 테스트가 잡습니다.

관광API 좌표를 한 번 더 검증하는 이유도 있습니다 — `제3땅굴` 은 관광API 에
`mapy=19.69, mapx=117.99`(남중국해)로 등록돼 있습니다.

## 4. 백엔드가 돌려야 할 것

임포트 경로를 고쳐도 **이미 저장된 장소는 사진이 계속 비어 있습니다.** 백필을 한 번 돌려야 합니다.

### 4-1. 현황 먼저 보기 (외부 API 안 부름, 몇 번 눌러도 안전)

```
GET /api/admin/places/image-status
```

```jsonc
{
  "total_places": 0,
  "with_image": 0,
  "without_image": 0,
  "by_source": [
    { "source": "TOUR_API", "total": 0, "with_image": 0, "without_image": 0 }
  ]
}
```

### 4-2. 백필 실행

```
POST /api/admin/places/backfill-images?max_places=50&naver_fallback=true
```

| 파라미터 | 기본값 | 설명 |
| --- | --- | --- |
| `max_places` | 50 | 이번 실행에서 시도할 장소 수. 장소당 외부 API 를 1~4회 부르므로 **나눠서 도세요** |
| `naver_fallback` | true | `false` 로 두면 관광공사 데이터만으로 채워지는 비율을 볼 수 있습니다 |

응답에 경로별 성공 건수와 **못 채운 장소 목록**이 나옵니다.

```jsonc
{
  "processed": 50,
  "filled_by_content_id": 41,
  "filled_by_name_match": 3,
  "filled_by_naver": 2,
  "still_missing": 4,
  "missing_places": [ { "place_id": 231, "name": "나눔의집", "source": "KAKAO" } ]
}
```

> ⚠️ 두 엔드포인트 모두 **인증이 붙어 있지 않습니다** (`AnchorDiscoveryController` 와 같은 상태).
> 아는 사람만 호출해야 합니다.

### 4-3. 네이버 키 발급

카카오 식당·카페 사진은 이 키가 없으면 계속 빕니다. 나머지(관광API 경로)는 키 없이도 채워집니다.

1. <https://developers.naver.com> 네이버 계정으로 로그인
2. **Application → 애플리케이션 등록**
3. 애플리케이션 이름: `itda`
4. **이용 목적에서 "비로그인 오픈 API" 를 체크합니다.** 검색 API 가 여기 속합니다.
   등록 폼에 "사용 API" 라는 항목은 없고, 검색을 따로 고르는 칸도 없습니다 —
   비로그인 오픈 API 는 클라이언트 아이디·시크릿만 헤더에 넣으면 바로 호출됩니다.
5. 등록하면 **Client ID / Client Secret** 발급 (무료, 하루 25,000건)

> 서비스 URL·Callback URL 은 "네이버 아이디로 로그인"(로그인 오픈 API)용 항목입니다.
> 검색만 쓸 것이므로 입력을 요구하면 `https://www.itda-travel.com` 을 넣고 넘어가면 됩니다.

넣을 곳은 **네 군데**입니다. 마지막 두 곳을 빠뜨리면 컨테이너에 전달되지 않아
예외 없이 조용히 꺼집니다.

| 위치 | 상태 |
| --- | --- |
| 로컬 `.env` | 직접 추가 (`.env.example` 에 항목 추가해 뒀습니다) |
| GitHub Secrets | **직접 추가해야 합니다** — `NAVER_SEARCH_CLIENT_ID`, `NAVER_SEARCH_CLIENT_SECRET` |
| `.github/workflows/deploy.yml` | 이번 작업에 포함됨 |
| `docker-compose.yml` | 이번 작업에 포함됨 |

## 5. 아직 안 되는 것

- **네이버 이미지 검색은 실제로 호출해 본 적이 없습니다.** 키가 없어서 검증을 못 했습니다.
  키를 넣고 `naver_fallback=true` 로 백필을 돌린 뒤, `filled_by_naver` 로 잡힌 장소의
  사진이 정말 그 가게인지 눈으로 몇 개 확인해 주세요.
- **네이버 이미지는 그 가게 실사진이라는 보장이 없습니다.** 블로그·카페 이미지를 유사도로
  가져오는 것이라, 제목 대조로 걸러도 틀릴 수 있습니다. 못 믿을 바에는 비우는 쪽을 택해
  제목에 상호가 없으면 아예 버립니다.
- **카카오 후보에는 영업시간이 없습니다.** 카카오 로컬 API 에 필드가 없어서, 카카오에서 온
  식당·카페는 `opening_hours` 가 `null` 이고 `night_open` 이 `false` 입니다.
- 사진을 못 구한 장소용 **기본 이미지(플레이스홀더)가 없습니다.** 프론트에서 `image_url` 이
  없을 때의 처리가 여전히 필요합니다.
