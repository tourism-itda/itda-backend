# 장소 사진·설명 채우기 + 카카오 후보 확정 버그 — 2026-09-17 (2026-09-18 갱신)

> `API_변경사항_프론트전달_2026-09-17.md` 의 후속입니다. **프론트가 고쳐야 할 것**(2장)과
> **백엔드에서 돌려야 할 배치**(4장)가 있습니다.

## 0. 네 줄 요약

- **카카오에서 온 식당·카페는 지금까지 루트에 담기지 못했습니다.** 고르면 "관광API 에서 장소를
  찾을 수 없습니다" 가 떴습니다. 확정 경로가 관광API 하나뿐이었기 때문입니다. 고쳤습니다.
- **사진과 설명이 비어 있던 원인**은 `place_image` 에 쓰는 코드가 없었고 `Place.ofTourApi` 에
  description 파라미터가 없었기 때문입니다. 관광API 는 둘 다 주고 있었습니다.
- 프론트는 `POST /api/places/import` 에 **`source`·`name`·`latitude`·`longitude` 를 추가**해야
  카카오 후보가 저장됩니다.
- 사진을 못 구한 장소는 **분류별 기본 이미지**가 나갑니다. `image_is_placeholder` 로 구분하세요.

## 1. 무슨 일이 있었나

### 1-1. 카카오 후보가 루트에 못 들어간 이유

식당·카페 후보는 두 군데서 옵니다 (`CandidateFinder`). 관광API 를 먼저 채우고,
`candidate_limit`(8) 에 모자라면 카카오 로컬(FD6/CE7)로 보충합니다.

그런데 확정 엔드포인트(`POST /api/places/import`)는 **무조건 관광API `detailCommon2` 에
contentId 로 조회**했습니다. 카카오 place id 는 contentId 가 아니므로 조회될 리가 없고,
카카오 후보는 **고르는 족족 404** 였습니다.

사진 유무와 상관이 있어 보였던 건 우연이 아닙니다 — **카카오 로컬 API 응답에는 이미지 필드가
아예 없습니다.** 실제 필드는 이게 전부입니다:

```
address_name, category_group_code, category_group_name, category_name,
distance, id, phone, place_name, place_url, road_address_name, x, y
```

### 1-2. 사진·설명이 비어 있던 이유

운영 DB 실측: `place` 231행, **`place_image` 0행**, `description` 은 `SEED` 121건만 채워져
있고 `TOUR_API`/`KAKAO` 111건은 전부 NULL 이었습니다.

관광API `detailCommon2` 는 `firstimage` 와 `overview` 를 같이 주고 `TourApiClient.findDetail`
도 둘 다 읽어 옵니다. 그런데 `place_image` 에 INSERT 하는 코드가 프로젝트에 하나도 없었고,
`Place.ofTourApi` 에는 description 파라미터가 아예 없었습니다. **둘 다 받아놓고 버린 것입니다.**

예: `왜고개`(contentId 2758125)는 관광API 에 사진도 있고 239자 설명도 있는데 우리 DB 는
양쪽 다 비어 있었습니다.

> 장소 상세 화면에서 설명이 보였던 것은 우리 DB 가 아니라 **프론트가 패스스루
> `GET /api/places/common?contentId=...` 를 직접 불러서** 였습니다. 그래서 관광API contentId 가
> 없는 **카카오 출처 장소는 상세에서도 설명이 없었습니다.**

## 2. 프론트가 고쳐야 할 것

### 2-1. `POST /api/places/import` — 필드 3개 추가

후보 목록(`CandidateView`)에 나간 값을 **그대로 더 실어 보내면 됩니다.**

```jsonc
{
  "external_id": "8260657",
  "place_type": "RESTAURANT",
  "source": "KAKAO",          // 신규 — CandidateView.source 를 그대로
  "name": "동북교자관 본점",     // 신규 — CandidateView.name
  "latitude": 37.28851,       // 신규
  "longitude": 127.01238      // 신규
}
```

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `source` | 아니오 | `TOUR_API` / `KAKAO`. **생략하면 `TOUR_API`** — 기존 요청이 그대로 동작합니다 |
| `name` | `KAKAO` 일 때 | 카카오 검증용 상호 |
| `latitude` / `longitude` | `KAKAO` 일 때 | 카카오 검증용 좌표 |

`name` 과 좌표가 **둘 다 없으면** 400 입니다.

> **왜 이름·좌표를 받나요?** 저장에는 쓰지 않습니다. 카카오 로컬 API 에는 id 단건 조회가 없어서,
> 받은 이름·좌표로 **검색한 뒤 id 가 일치하는 결과만** 채택합니다. 저장값은 전부 카카오 응답에서
> 오므로 클라이언트가 값을 꾸며도 임의의 place 를 밀어 넣을 수 없습니다.

### 2-2. `image_url` 은 이제 항상 채워집니다 + `image_is_placeholder`

`RoutePlaceView` 에 필드가 하나 늘었습니다.

```jsonc
{
  "place_id": 244,
  "name": "단박왕돈까스",
  "image_url": "/images/place-types/restaurant-japanese.svg",
  "image_is_placeholder": true,     // 신규
  ...
}
```

| | 뜻 |
| --- | --- |
| `image_is_placeholder: false` | 관광API 에서 받은 **실제 사진** |
| `image_is_placeholder: true` | 분류에 맞는 **기본 이미지**. "사진 있음" 배지를 붙이면 안 됩니다 |

기본 이미지는 `/images/place-types/*.svg` 로 백엔드가 정적 서빙합니다(인물 이미지
`/images/persons/...` 와 같은 방식). 한식·중식·일식·양식·음식점·카페·관광지 7종입니다.

## 3. 사진·설명이 채워지는 순서

전부 **관광API 에서만** 가져옵니다.

1. **`detailCommon2`** — contentId 를 들고 있으면 바로. `firstimage` + `overview` 를 한 번에 받습니다.
2. **좌표+이름 매칭** — contentId 가 없는 장소(카카오·시드 출처)는 같은 곳을 관광API 에서 찾아
   contentId 를 알아낸 뒤 1번을 합니다.
3. **`detailImage2`** — 갤러리용 추가 사진. `firstimage` 가 비어도 사진이 있는 경우를 여기서 건집니다.

실측 (시드 앵커 18곳):

| 경로 | 결과 |
| --- | --- |
| `detailCommon2.firstimage` | **16 / 18** |
| `detailImage2` 로 추가 확보 | +1 (전일빌딩245 — firstimage 없음, detailImage2 5장) |
| 관광API 에 아예 없음 | 1 (창덕궁 낙선재 — 양쪽 다 0장) |
| **카카오 식당을 관광API 로 역매칭** | **0 / 15** |

마지막 줄이 핵심입니다. 카카오 후보는 **정의상 "관광API 에 없어서 카카오로 넘어온 것"** 이라
역매칭이 되지 않습니다. 그래서 기본 이미지를 씁니다.

> **네이버 이미지 검색을 쓰지 않는 이유:** 2026-07-31 자로 네이버 개발자센터에서 검색 API
> 신규 발급이 끊겨 NAVER API Hub 로만 받을 수 있고(인증 헤더·도메인이 다릅니다),
> 2026-09-07 시행 특약이 검색 API 를 "네이버 검색 결과를 제공하기 위한 목적" 으로 한정합니다.
> 남의 블로그 사진을 우리 가게 카드에 박는 것은 그 목적이 아니고, 사진의 저작권도 글쓴이에게
> 있습니다.

### 왜 좌표와 이름을 둘 다 보나

한쪽만 보면 둘 다 틀립니다. 실측 예:

| 방식 | 결과 |
| --- | --- |
| 이름만 (`searchKeyword2`) | 우리가 `거제포로수용소`, 관광API 가 `거제도 포로수용소` → **0건** |
| 좌표만 | `학도의용군 전승기념관` 에 근처 **죽림사** 사진, `5.18기념공원` 에 **광주일신여상** 사진 |
| 좌표 + 이름 유사도 | `거제도 포로수용소 유적공원` 채택(0.75), `포로수용소유적박물관` 거부(0.462) |

유사도는 글자 2-gram 자카드, 임계값 0.6 (`PlaceNameSimilarity`). 실측값을
`PlaceNameSimilarityTest` 에 박아 뒀으니 임계값을 건드리면 테스트가 잡습니다.

관광API 좌표도 한 번 더 검증합니다 — `제3땅굴` 은 `mapy=19.69, mapx=117.99`(남중국해)로
등록돼 있습니다.

## 4. 백엔드가 돌려야 할 것

임포트 경로를 고쳐도 **이미 저장된 231곳은 그대로 비어 있습니다.** 백필을 돌려야 합니다.

### 4-1. 현황 보기 (외부 API 안 부름, 몇 번 눌러도 안전)

```
GET /api/admin/places/backfill-status
```

```jsonc
{
  "total_places": 231,
  "with_image": 0,
  "without_image": 231,
  "without_description": 111,
  "by_source": [ { "source": "TOUR_API", "total": 0, "with_image": 0, "without_image": 0 } ]
}
```

### 4-2. 백필 실행

```
POST /api/admin/places/backfill?max_places=50
```

장소당 외부 API 를 1~5회 부르므로 **나눠서 도세요**(231곳이면 5번쯤).

```jsonc
{
  "processed": 50,
  "images_filled_by_content_id": 41,
  "images_filled_by_name_match": 3,
  "descriptions_filled": 44,
  "not_found_in_tour_api": 6,
  "missing_places": [ { "place_id": 244, "name": "단박왕돈까스", "source": "TOUR_API" } ]
}
```

`not_found_in_tour_api` 는 **실패가 아닙니다.** 그 장소들은 기본 이미지로 나갑니다.

> ⚠️ 두 엔드포인트 모두 **인증이 붙어 있지 않습니다**
> (`AnchorDiscoveryController` 와 같은 상태). 아는 사람만 호출해야 합니다.

## 5. 아직 안 되는 것

- **카카오 후보에는 영업시간이 없습니다.** 카카오 로컬 API 에 필드가 없어서, 카카오에서 온
  식당·카페는 `opening_hours` 가 `null` 이고 `night_open` 이 `false` 입니다.
- **카카오 후보에는 설명도 없습니다.** 관광API contentId 가 없어 패스스루도 안 됩니다.
- 기본 이미지는 7종뿐이라 **같은 분류의 가게가 전부 같은 그림**입니다. 디자인이 정해지면
  `src/main/resources/static/images/place-types/` 의 SVG 만 갈아 끼우면 됩니다.

## 6. 참고 — 카카오를 빼면 어떻게 되나

"사진이 있는 후보만 쓰자"는 선택지를 실측했습니다. 운영 구간 60개 기준:

| 슬롯 | 구간 | 현재 평균 | 관광API만 | 후보 0개가 되는 구간 |
| --- | ---: | ---: | ---: | ---: |
| 식당 | 40 | 8.0 | 6.8 | 6 (15%) |
| 카페 | 20 | 7.8 | 4.0 | **7 (35%)** |
| 전체 | 60 | 7.9 | 5.9 | **13 (22%)** |

대부분 구간은 상한(8개)을 그대로 채우지만 **5곳 중 1곳은 후보가 0개**가 됩니다. 사진 때문에
"선택지가 아예 없는 칸"을 만드는 건 대가가 커서 **카카오는 유지**하기로 했습니다.
