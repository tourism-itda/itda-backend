## 0. 왜 이 문서가 필요한가

앱의 메인 기능은 **"콘텐츠를 고르면 그 작품과 관련된 여행 코스가 나온다"** 이다.
루트를 짜는 엔진(`planner.route.*`)은 이미 완성돼 있다. 남은 건 그 **입력**, 즉
`content_place`(콘텐츠 ↔ 장소 매핑)를 **어떻게 채우느냐** 하나다.

이게 어려웠던 이유는 질문 세 개가 뒤엉켜 있어서다.

| | 질문 | 성격 | 푸는 법 |
|---|---|---|---|
| A | 이 장소가 이 작품과 정말 관련 있나 | 출처 확인 문제 | 근거 + 등급 (2장) |
| B | 관련 있어도 갈 만한 곳인가 | 데이터 필터 | 하드필터 (3장) |
| C | 루트에 넣을 수 있나 | 계산 문제 | ✅ 해결됨 — `SpotScorer`/`DetourFilter` |

A와 B를 뭉쳐 판단하려니 "주관적"으로 느껴졌던 것이다. 갈라야 한다.

## 1. 실측으로 확인한 TourAPI 동작 (2026-08-26)

설계의 전제가 되는 사실들. **여기 적힌 건 전부 실호출로 확인했다.**

### 1-1. `searchKeyword2` 는 제목(title) 부분일치다

overview 는 **검색 대상이 아니다.** 검색 파라미터에도 응답 필드에도 overview 가 없다.
따라서 "장소 소개글에 작품명이 있는 곳을 찾아줘"는 **API 로 불가능**하다.

```
keyword=덕수궁  →  "덕수궁 대한문", "덕수궁 돌담길"     (부분일치 확인)
```

### 1-2. 촬영지 관용어 검색 — 총량이 작다

```
세트장   8건      촬영지 14건      드라마 12건
민속마을 7건      영화  42건       고택  109건
```

중복 빼면 촬영지 관련은 **30건 내외**. 기대했던 "전수 확보"는 규모가 작다.
**다만 30건이면 사람이 반나절에 전부 검토할 수 있다**는 뜻이기도 하다.

### 1-3. ❌ cat3 로 촬영지를 거를 수는 없다

세트장들의 `cat3` 가 전부 `A02030400` 이길래 필터로 쓰려 했으나, 이 코드는 **"이색체험"**
으로 전국 **359건**이고 그 안에 케이블카·복지관·창작캠퍼스가 섞여 있다. 샘플 20건 중
촬영지 키워드를 가진 건 **0건**. **이 경로는 폐기.**

### 1-4. ✅ 인물명 검색은 된다 (예상 밖의 수확)

당초 "장소 이름에 인물명이 없으니 안 될 것"이라 판단했는데 **틀렸다.**

```
이순신 → 17건   (관광지 6, 여행코스 3, 축제 2, 문화시설 3, 레포츠 2, 음식 1)
정조   →  7건
```

이유: 관광지 이름에 인물명이 없어도 **축제·기념관·여행코스** 제목에는 들어간다.
예) `아산 성웅 이순신축제`, `여수 이순신공원`, `정조대왕 능행차 공동재현`

→ **`explore.entity.Person`(왕조별 역사인물) 테이블이 그대로 검색어 사전이 된다.**

### 1-5. ✅ 여행코스(contentTypeId=25) — 가장 큰 발견

관광공사가 **이미 큐레이션해 둔 코스**가 있고, `detailInfo2` 로 구성 장소를 꺼낼 수 있다.

```
searchKeyword2(keyword=이순신, contentTypeId=25)
  → [1937588] 과거급제를 꿈꾸던 청년 이순신이 살던 그곳에서 놀기
  → [2371903] 여수 앞바다와 이순신 유적지를 찾아 떠나는 여행
  → [1870729] 이순신 장군의 흔적을 따라가는 여행

detailInfo2(contentId=1937588, contentTypeId=25)
  → 현충사 (125945)
  → 아산 외암리 민속마을 (126001)
  → 점심식사(목화반점) (800487)
  → 당림미술관 (130268)
  → 아산레일바이크 (1936362)
  → 파라다이스 스파도고 (631934)
```

**점심 식당까지 포함된 완성된 하루 코스**다. `subcontentid` 가 실제 관광API contentId 라
좌표·영업시간·이미지를 이어서 조회할 수 있다. 우리 `DayTemplate` 이 만들려는 결과물이
이미 데이터로 존재한다.

커버리지는 얇다 (이순신 3건, 정조 1건). **골격으로 쓰고 부족분을 우리 엔진이 채운다.**

### 1-6. ⚠️ 연관 관광지 (`TarRlteTarService1`) — 강력하지만 함정 셋

한국관광공사가 실제 관광 행태로 만든 **"이 관광지 간 사람이 함께 간 곳" 순위**다.
우리가 스코어를 지어낼 필요를 없애주는 데이터.

```
경복궁(11/11110)   → 50건: 남산케이블카, 북촌한옥마을, 광장시장, 토속촌삼계탕, 청와대 …
수원화성(41/41115) → 50건: 스타필드수원, 화성행궁, 수원시립미술관, 지동시장 …
한국민속촌(41/41463) → 50건: 스타필드수원, 에버랜드, 롯데아울렛기흥 …
```

**함정 ①** `areaCd` · `signguCd` · `baseYm` **셋 다 필수**다.
`docs/tourism_api_guide.md` 가 뒤의 둘을 선택(X)으로 적어놨는데 **문서가 틀렸다.**

**함정 ②** `signguCd` 는 **구(區) 단위까지** 정확해야 한다.

```
수원화성 + signguCd=41110 (수원시)   → 0건
수원화성 + signguCd=41115 (팔달구)  → 50건   ← 시(市) 코드로는 절대 안 나온다
```

**함정 ③** 커버리지가 전부가 아니다.

```
✅ 경복궁 · 수원화성 · 한국민속촌 · 뮤지엄산
❌ 창덕궁 · 남한산성 · 대장금파크    (전부 0건)
```

→ **"있으면 쓰고 없으면 폴백"** 으로 설계해야 한다. 폴백은 `locationBasedList2` 반경 검색.

`baseYm` 은 202412~202606 어느 값이든 같은 결과가 나온다. 최신 달을 계산해 넣으면
아직 집계 안 된 달을 물어 0건이 될 수 있어 **확인된 값(`202503`)으로 고정**했다.

## 2. 매핑 방법 — 2층 구조

핵심은 **앵커를 적게 만들고 나머지는 관광API가 실시간으로 채우게** 하는 것이다.

```
 콘텐츠 (TMDB: 제목·줄거리·키워드 / Person: 인물·왕조)
    │
    ▼  검색어 세트 { 작품명, 인물명, 사건·지명 }
    │
┌───┴─────────────────────────────────────────────────┐
│ 층 1 · 앵커  — 작품과 실제로 관련된 곳                │
│   작품당 1~3곳이면 충분. 오프라인 + 사람 검수.        │
│   저장 대상 (= content_place)                        │
└───┬─────────────────────────────────────────────────┘
    │  앵커 좌표 · 앵커 이름
┌───┴─────────────────────────────────────────────────┐
│ 층 2 · 확장  — 앵커 주변에서 분위기 맞는 곳           │
│   수십 곳. 100% 실시간 TourAPI. 저장 안 함.          │
└───┬─────────────────────────────────────────────────┘
    ▼
 DetourFilter → SpotScorer → RoutePlanner  (기존 코드 그대로)
    ▼
 하루 루트
```

**작품 20편 × 앵커 2곳 = 40행.** 손으로 채울 수 있는 양이다.
이게 곧 시드 데이터 · 데모 데이터 · 자동 판정 정답셋 세 가지를 동시에 해결한다.

## 3. 층 1 — 앵커 만들기 (상세)

### 3-1. 발견 경로 5개

우선순위 순. 위에서부터 돌리고 앵커 2곳이 차면 멈춘다.

| # | 경로 | 호출 | 수율 | 등급 |
|---|---|---|---|---|
| A | **작품 제목 직접** | `searchKeyword2(작품명)` | 낮음 (세트장 있는 작품만) | **A** |
| B | **인물명** | `searchKeyword2(Person.name)` | 사극에서 높음 | **A** |
| C | **여행코스** | `searchKeyword2(인물명, type=25)` → `detailInfo2` | 얇지만 품질 최상 | **A** |
| D | **사건·지명** | `searchKeyword2(지명)` | 높음 | **B** |
| E | **LLM 후보 + 실재 검증** | LLM이 장소'이름'만 → `searchKeyword2` 로 확인 | 보정용 | **B/C** |

#### 경로 A — 작품 제목

```
searchKeyword2(keyword="대장금")
  → 용인 대장금파크 (2661408)  ✅
searchKeyword2(keyword="태조왕건")
  → 0건  ❌  (등록명·띄어쓰기에 민감. "태조 왕건" 등 변형 필요)
```

세트장·테마파크는 이름에 작품명이 박혀 있다. **근거가 관광API 자체라 A등급 확정.**

#### 경로 B — 인물명 (사극의 주 경로)

`content` → `Person`(왕조·인물) 연결만 있으면 자동으로 돈다.
`explore` 패키지의 `Person`/`Kingdom`/`HistoricalPersonData` 를 그대로 쓴다.

```
콘텐츠 「왕이 된 남자」 → Person: 광해군 (JOSEON)
  → searchKeyword2("광해군")
```

⚠️ 결과에 **여행코스(25)·축제(15)가 섞여 있고 이들은 좌표가 비어 있는 경우가 흔하다.**
`TourApiClient.searchByTitle()` 은 그래서 좌표 없음을 이유로 버리지 않는다 — 이름만으로도
앵커 후보로 의미가 있기 때문이다. 좌표는 나중에 `detailCommon2` 로 채운다.

#### 경로 C — 여행코스 (품질 최상)

```java
// TourApiClient
List<TourApiPlace> courses = searchByTitle("이순신", CONTENT_TYPE_COURSE, 10);
List<TourApiCourseStop> stops = findCourseStops(courses.get(0).contentId());
// stops[i].subContentId() 로 detailCommon2 → 좌표·이미지·주소 확보
```

코스가 잡히면 **앵커 + 루트 골격 + 식사 슬롯까지 한 번에** 얻는다.
`subname` 에 `"점심식사(목화반점)"` 처럼 슬롯 성격이 드러나기도 한다.

#### 경로 D — 사건·지명

`남한산성`, `행주산성`, `강화도` 처럼 작품 배경 지명. 지명은 곧 장소명이라 잘 잡힌다.
다만 "작품 관련"의 근거는 약하므로 **B등급**.

#### 경로 E — LLM 후보 + 실재 검증

**LLM에게 절대 묻지 않을 것: 좌표 · 주소 · place_id. 100% 환각이다.**
LLM은 **장소 "이름"만** 내고, 실재 여부는 `searchKeyword2` 가 판정한다.
즉 **TourAPI 가 환각 필터 역할**을 한다 — 없는 장소를 대면 조회가 0건이라 자동 탈락.

프롬프트도 `"촬영지 알려줘"`(❌)가 아니라
`"이 근거 텍스트가 관련성을 뒷받침하나"`(✅)로 묻는다.
`SpotCurator` 주석의 역할 분담(코드=계산, LLM=판단)과 같은 원칙이다.

### 3-2. 이름 → contentId 정규화 (환각 필터)

모든 후보 이름은 이 단계를 통과해야 한다. **실패하면 그 자리에서 탈락.**

표기가 흔들리므로 최대 3회 시도:

1. 원문 그대로
2. 괄호·수식어 제거 — `"운현궁(서울)"` → `"운현궁"`
3. 접미어 변형 — `"OO세트장"`, `"OO촬영장"`, `"OO테마파크"`

지역을 아는 경우 `areaCode` 를 함께 넘겨야 동명 장소가 안 섞인다.

### 3-3. 하드필터 (판단 없음, 순수 코드)

- **좌표 없음** → 탈락 (동선 계산 불가. 단 3-1 경로 B/C 처럼 나중에 채울 수 있으면 보류)
- `contentTypeId` **32(숙박)·38(쇼핑) 제외**, 12·14·15·25 허용
- `firstimage` 없음 → 탈락이 아니라 **등급 강등** (지방 사적지는 이미지가 자주 빈다)
- **200m 이내 중복 병합** (같은 궁궐의 여러 문이 별도 contentId 로 등록돼 있다)

### 3-4. 근거 등급 — 판정을 "취향"에서 "출처"로

| 등급 | 조건 | 처리 |
|---|---|---|
| **A** | 경로 A/B/C — 관광API 데이터 자체가 근거 | 자동 통과 |
| **B** | 경로 D/E — 근거 URL 이 살아 있고 본문에 (장소명 AND 작품명) 동시 등장 | 사람 검수 후 통과 |
| **C** | LLM 주장만, 교차검증 실패 | **DB에 넣되 노출 안 함** — 관리자 검수 큐 |

**노출 기준은 B 이상으로 못 박는다.** 그러면 팀 회의의 대화가
"이 장소 관련 있어 보이는데?" 에서 **"몇 등급이야?"** 로 바뀐다. 그게 이 표의 목적이다.

⚠️ **팩트체크 텍스트는 반드시 사람 검수.** LLM 생성 역사 서술을 그대로 노출하면
틀린 역사를 배포하게 된다. 출처 표기 + 검수 플래그는 선택이 아니라 필수다.

## 4. 층 2 — 확장 (100% 실시간)

앵커가 정해지면 나머지는 전부 TourAPI 가 답한다. **저장하지 않는다.**

### 4-1. 연관 관광지 (1순위)

```java
// 1) 앵커 주소 → 법정동 시군구코드
Optional<String> signguCd = ldongCodeResolver.resolveSignguCd(anchor.getAddress());
// "경기도 수원시 팔달구 정조로 910" → "41115"

// 2) 연관 관광지
placeService.searchRelatedByKeyword(anchor.getName(), signguCd.substring(0,2), signguCd, null, 1, 50);
```

결과의 `rlteCtgrySclsNm`(한식·카페/찻집·역사유적지·시장·전시시설…)이 우리 루트 슬롯
(SPOT/RESTAURANT/CAFE)에 그대로 매핑된다. `rlteRank` 가 정렬까지 끝내 준다.

**0건일 수 있다 (커버리지 ~50%). 반드시 4-2 로 폴백.**

### 4-2. 반경 + 테마 (폴백 · 항상 동작)

`CandidateFinder` 가 이미 하는 일이다. `TourApiCategory.queryParamsFor()` 에 콘텐츠별
cat3 를 주입할 수 있게 오버로드만 추가하면 된다.

콘텐츠 성격 → cat3 매핑:

| 콘텐츠 성격 | cat3 |
|---|---|
| 궁중 사극 | `A02010100`(고궁) · `A02010700`(유적지/사적지) · `A02010400`(고택) |
| 전쟁·의병 | `A02010700` · `A02010200`(성) · `A02011000`(안보관광) |
| 민초·시장 | `A02010600`(민속마을) · `A02030200`(전통체험) |
| 근현대 | `A02050600`(유명건물) · `A0206`(문화시설) · `A02030600`(이색거리) |

> cat3 만 단독으로 넘기면 필터가 안 먹는다. **cat1·cat2 를 계층으로 함께** 보내야 한다
> (`TourApiCategory` 클래스 주석 참고).

콘텐츠 → cat3 번역에 LLM 을 쓴다면 여기가 **안전한 자리**다. 출력이 **닫힌 코드 집합**이라
환각이 원천 차단되고, 잘못 골라도 엉뚱한 카테고리일 뿐 없는 장소를 지어내지 않는다.

### 4-3. 날짜 기반 축제 (실시간의 존재 이유)

```java
placeService.searchFestivals(travelDate, ..., areaCode, ...);
```

같은 콘텐츠·같은 지역이라도 **날짜에 따라 루트가 달라진다.** DB 스냅샷으로는 불가능한
기능이고, "왜 실시간 연동이어야 하는가"의 답 그 자체다. 공모전 어필 포인트.

## 5. 랭킹과 "추천 이유"

신호 4개. 전부 계산 가능하고 LLM 없이 문구까지 만들 수 있다.

1. **근거 등급** — A > B > C
2. **연관 순위** — `rlteRank` (있을 때)
3. **테마 일치** — cat3 가 콘텐츠 코드 집합에 있는가
4. **동선** — `DetourFilter.detourMeters()` (기존)

각 장소에 **추천 이유 한 줄**을 이 신호에서 자동 생성한다:

```
"「대장금」 촬영지"                             ← 경로 A
"광해군의 흔적이 남은 곳"                       ← 경로 B
"경복궁 방문객이 함께 찾은 곳 · 연관순위 3위"    ← rlteRank
"촬영지 창덕궁에서 1.2km · 같은 조선 궁궐"       ← 테마+동선
```

**이 한 줄이 메인 기능의 완성도를 결정한다.** 장소 목록만 뿌리면 아무리 정확해도
사용자도 심사위원도 "왜 이 장소?"에 답을 못 얻는다.

### 앵커가 0곳인 작품

현대 로맨스 등은 경로 A~E 가 전부 0건일 수 있다. 이때는 **배경 지역만 알면** cat3 매칭으로
루트는 나온다. 다만 문구를 정직하게 바꾼다 — "촬영지"가 아니라 **"이 작품 분위기의 코스"**.
**근거 등급이 UI 문구를 결정하게 만들면 거짓말을 안 하게 된다.**

## 6. 저장 정책 (공모전 실시간 연동 권장 대응)

| 구분 | 예시 | 정책 |
|---|---|---|
| 관광API 소유 데이터 | title · addr · overview · firstimage · 영업시간 · 전화 | **저장 금지 → 응답 조립 시 실시간 조회** |
| 우리가 만든 데이터 | itinerary · bookmark · review · **content_place + 근거·등급** | 저장. 장소는 **contentId 만** 참조 |
| 캐시 | 코드표(ldongCode 등), 동일 파라미터 응답 | 저장 아님. 인메모리 + 짧은 TTL, 재기동 시 소멸 |

한 문장으로: **"우리는 관광API의 사본이 아니라 인덱스를 갖는다."**

좌표만은 예외로 저장한다 — `DetourFilter`/`SpotScorer` 가 후보 수십 건의 거리를 계산해야
하는데 건건이 API 를 부를 수 없기 때문이다. **"계산에 필요한 최소값만, 표시값은 전부 실시간"**
이 방어 가능한 선이다.

심사에서 설명할 문장:
> 관광API를 복제하지 않고, **관광API에 없는 레이어(콘텐츠 연결·역사 근거)만 생성해**
> 실시간 데이터 위에 얹었다.

## 7. 스키마 — 팀 합의 필요 ⚠️

`ContentPlace` / `ContentFactCheck` 는 **박세현 소유 파일**이라 손대기 전에 합의가 필요하다.

```java
ContentPlace {
    content_id
    external_content_id   // ★ place_id 대신 관광API contentId 를 직접 참조
    relation_type         // FILMING | HISTORICAL | EXHIBIT | SUPPORT
    evidence              // 근거 원문
    evidence_source       // 출처 URL
    grade                 // A | B | C
    verified              // 사람 검수 여부
    recommend_order
}
```

- **`relationType` 분리가 중요하다.** 사극은 촬영지(세트장)와 역사 배경지(실제 궁궐)가
  **다른 장소**다. 한 리스트로 뭉치면 판정 기준을 못 세운다.
- `ContentFactCheck` 에 `place_id`(nullable) 추가 → 팩트체크가 붙는 장소 = 상위 후보.
  판정 규칙이 자동으로 생긴다.

#### 경로 A 의 등급을 낮춘 이유 (중요)

3-1 표는 경로 A 를 A등급으로 적어놨지만 **그대로 구현하면 안 된다.**
`searchKeyword2` 는 제목 부분일치라 제목이 지명인 작품에서 무관한 장소가 쏟아진다.

```
「인천」 → 인천대공원 · 인천차이나타운 · 인천대교      ← 작품과 무관
「명량」 → 명량대첩해전사기념전시관 · 울돌목            ← 진짜 관련
```

**둘 다 "제목 일치"라 문자열 규칙으로는 못 가른다.** 그래서 가르지 않고 사람에게 넘긴다.

| 조건 | 등급 |
|---|---|
| 이름에 촬영지 관용어(세트·촬영장·촬영지·테마파크·파크·드라마·영화)까지 있음 | **A** — 자동 통과 (「대장금」→ 용인 대장금파크) |
| 그 외 제목 일치 | **B** — 사람 검수 |

C 는 이 스크립트에서 나오지 않는다. 모든 후보가 `searchKeyword2` 로 실재가 확인된 것들이라
문서 3-4 의 C 정의("LLM 주장만, 교차검증 실패")에 해당하지 않는다.

#### 전쟁·사극 콘텐츠에서는 경로 D 가 주 경로다

현재 콘텐츠 23편이 전부 전쟁·사극이다. 이 경우 **작품 제목보다 사건·지명이 훨씬 정확한 신호**다.

```
「인천」        제목 → 인천대공원          지명 → 인천상륙작전기념관 · 월미도 · 자유공원
「태극기 휘날리며」 제목 → 0건               지명 → 다부동 · 전쟁기념관 · 낙동강
```

그래서 같은 B등급 안에서 **C(코스) → B(인물) → D(지명) → A(제목)** 순으로 정렬해
검수자가 위에서부터 훑다가 좋은 걸 먼저 만나게 했다. 이 순서가 검수 품질을 좌우한다.

23편치 지명 키워드는 **`scripts/seed-keywords.csv`** 에 넣어 뒀다 (55건).
장소 "이름"만 적었고 실재 판정은 `searchKeyword2` 가 한다 — 3-1 경로 E 의 환각 필터 원칙 그대로다.
「무사」·「모가디슈」·「마이웨이」는 해외 배경이라 의도적으로 비웠다(5장 "앵커가 0곳인 작품").

`content_place` 는 박세현 소유 엔티티라 **컬럼을 늘리지 않았다**(7장). 근거·등급·경로는 CSV 에만
남으므로 **검수한 CSV 를 저장소에 함께 커밋**해 감사 흔적을 남길 것.
