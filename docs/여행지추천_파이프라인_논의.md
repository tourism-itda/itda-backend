# 영화 → 실화 → 여행지 추천 — 결정 사항 & 남은 논의

> 목적: itda 메인 기능인 **"콘텐츠를 고르면 그 작품의 하루 여행 코스가 나온다"** 의
> 현재 구현을 공유하고, **정해진 4가지를 실제 데이터에 적용해본 결과**와
> 그 결정에서 **새로 생긴 질문 6가지**에 대해 의견을 받는다.
>
> 아래 숫자는 전부 2026-09-14 기준 실측이다. (배포 API + `scripts/seed-candidates.csv` 78행 + `feat/tourapi-fix` 코드)

## 1. 현재 로직 (as-is)

### 전체 흐름

```
콘텐츠 (TMDB 영화 23편)
   │
   ▼  검색어 세트 { 작품명 · 인물명 · 사건/지명 }
   │
[층 1] 앵커 발견  ── scripts/seed-content-places.ps1 -Mode discover
   │   경로 D(지명) → B(인물) → A(제목) → C(여행코스)  순으로 TourAPI 검색
   │   하드필터(좌표없음/숙박·쇼핑/200m중복) → 등급 판정
   ▼
후보 CSV 78행 ──▶ 사람 검수(approve=Y) ──▶ build-sql ──▶ content_place
   │                      ▲
   │                      └── 🔴 지금 여기서 멈춰 있음 (0/78 검수, content_place 0건)
   ▼
[층 2] 루트 조립  ── POST /api/itineraries/route
   │   content_place 로드 → SpotScorer(동선·순서·야간) → SpotCurator(Claude 택1)
   │   DayTemplate:  장소 → 식당(점심) → 카페 → 장소 → 식당(저녁) → 장소
   ▼
GET /api/itineraries/route/candidates  ── 구간별 식당/카페 후보 (TourAPI 반경 + 우회거리순)
   ▼
사용자가 지도에서 직접 채움 → 일정 저장
```

### 단계별 상세

| 단계 | 위치 | 동작 |
| --- | --- | --- |
| ① 검색어 생성 | `scripts/seed-keywords.csv` (수기 55건) | 작품별 **사건·지명** 키워드. 인물명은 `content_person`이 비어 있어 **미사용** |
| ② 앵커 발견 | `seed-content-places.ps1 -Mode discover` | 경로 D→B→A→C 순 `searchKeyword2` 호출 |
| ③ 하드필터 | 〃 | 좌표 없음 탈락 · 숙박(32)·쇼핑(38) 제외 · 200m 중복 병합 |
| ④ 등급 판정 | 〃 | 이름에 촬영지 관용어 있음 → **A(자동통과)**, 그 외 → **B(사람검수)** |
| ⑤ 검수 | 사람 (CSV `approve` 열) | **현재 0/78** |
| ⑥ 적재 | `-Mode build-sql` → psql | `place` + `content_place` INSERT |
| ⑦ 촬영지 선택 | `RoutePlanner.selectSpots()` | 사용자 선택 or 자동. 최대 3곳 (`DayTemplate.MAX_SPOTS`) |
| ⑧ 후보 좁히기 | `SpotScorer` | 우회거리 **0.6** + 순서 **0.3** + 야간운영 **0.1** |
| ⑨ 택 1 | `SpotCurator` (Claude Haiku) | 좁혀진 5곳 중 1곳 + 이유. 실패 시 점수 1등 폴백 |
| ⑩ 템플릿 | `DayTemplate` | 촬영지 3곳 기준 6슬롯 |
| ⑪ 시간 계산 | `TimelineEstimator` | 10:00 시작 · 체류 120/90/60분 · **이동 25km/h** |
| ⑫ 식당·카페 | `CandidateFinder` → `/route/candidates` | TourAPI 반경 → 우회거리 ≤ 허용거리(기본 3km) → 오름차순 |

### 현재 막혀 있는 것

| 항목 | 값 |
| --- | --- |
| **`content_place`** | **0건** → 추천/루트 API가 전부 404 |
| 검수 진행률 | **0 / 78** |
| `content_person` | 0건 → 경로 B(인물명 검색)가 안 돎 |

## 2. 결정된 것 4가지 — 데이터에 적용해본 결과

### ✅ 결정 1 — 시대 범위: **제1공화국까지. 1960년 이후 현대사는 수집 제외**

`Kingdom` enum의 마지막 값 `FIRST_REPUBLIC_OF_KOREA`(1948~1960)가 그대로 경계가 된다. **한국전쟁물은 포함.**

**적용 결과 — 23편 중 3편 제외, 20편 대상**

| 제외 작품 | 배경 | 앵커 후보 |
| --- | --- | --- |
| 서울의 봄 | 1979 | 5건 (경복궁·국립서울현충원) |
| 모가디슈 | 1991 | 0건 |
| 연평해전 | 2002 | 2건 |

**이 결정이 같이 해결하는 것:** 지금 DB에 **「연평해전」(2002)이 `JAPANESE_COLONY`(일제강점기)로 저장돼 있다.** 「모가디슈」(1991)도 `FIRST_REPUBLIC_OF_KOREA`로 잘못 들어가 있다. 둘 다 **Claude가 지어낸 게 아니라 고를 수 있는 enum 값이 없어서** 생긴 오류다. 범위 밖을 수집 단계에서 쳐내기로 했으니 **enum을 넓힐 필요가 없어졌다.** 대신 **수집 시점에 시대 범위 필터가 새로 필요하다.**

> ⚠️ 「무사」는 고려 배경이라 시대 범위로는 안 걸러진다. 하지만 허구 서사고, 앵커 2건이 전부 오매칭(`"무사"` → **충무사** = 이순신 사당)이라 검수에서 탈락한다. → 결과적으로 앵커 0건이 되어 **논의 4**로 넘어간다.

---

### ✅ 결정 2 — 장소 우선순위: **역사 현장 > 촬영지 > 일반 명소**

**적용해보니 문제가 하나 나왔다 — 이 분류를 자동으로 못 매긴다.**

장소 후보 63건을 이름 기준으로 자동 분류해봤다.

| 성격 | 자동 분류 결과 |
| --- | --- |
| 역사 현장 | 31건 |
| **촬영지** | **0건** |
| 일반 명소 | 37건 |

그런데 **'일반 명소'로 빠진 것 중 상당수가 실제로는 역사 현장이다.**

```
제승당 · 한산도          ← 한산도대첩 유적인데 이름에 '기념관/유적'이 없어서 누락
명량해협 울돌목          ← 명량대첩 현장
개태사(논산)            ← 왕건이 창건한 절
서울 삼전도비           ← 병자호란 현장
북촌마을 4·3길          ← 제주 4·3 현장
자유공원(인천) · 월미도    ← 인천상륙작전 현장
```

반대로 **고구려대장간마을**은 '일반 명소'로 분류됐지만 실제로는 드라마 세트장 = **촬영지**다.

**원인:** 현재 CSV에 `category` 컬럼이 있지만 값이 `관광지(47건) / 문화시설(15건) / 축제공연행사(1건)` 세 가지뿐이다. TourAPI가 주는 **세부 분류(cat3)를 스크립트가 저장하지 않고 있다.** 그래서 자동 분류의 근거가 없다.

→ **이게 논의 1이 됐다.** (relation_type을 누가 어떻게 매기나)

**또 하나:** 후보에 **여행코스(contentTypeId=25)가 5건** 장소인 척 섞여 있다. (`"고구려의 옛 흔적을 만나다"`, `"연천에서 만나는 고구려"`) 장소가 아니라 코스라 앵커가 될 수 없다. **검수에서 빼거나 스크립트가 걸러야 한다.**

---

### ✅ 결정 3 — 식당·카페는 작품과 엮지 않는다 (주변 검색 유지)

현행 유지. `CandidateFinder`가 좌표 반경으로 찾고, 사용자가 지도에서 직접 고른다. **코드 변경 없음.**

**다만 문구는 정리해야 한다.** 식당·카페에 작품 관련 근거가 없다는 걸 인정한 거니까, UI에서 "추천 코스"처럼 전부 큐레이션된 것처럼 보이면 안 된다.

```
촬영지/역사현장  →  "「명량」의 무대"          (근거 있음)
식당·카페        →  "주변 맛집" / "근처 카페"   (근거 없음 — 정직하게)
```

---

### ✅ 결정 4 — 코스는 **지역 단위**. 차로 이동 가능한 하루 범위

**적용 결과 — 작품 × 시도로 쪼개면 27개 조합, 그중 하루 코스가 되는 건 8개**

기준: 앵커 3곳 이상 + 앵커 간 최대 직선거리 60km 이하

| 작품 | 지역 | 앵커 | 최대거리 | 판정 |
| --- | --- | --- | --- | --- |
| 인천 | 인천 | 11건 | 21.3km | ✅ |
| 인천상륙작전 | 인천 | 5건 | 8.0km | ✅ |
| 남한산성 | 경기 | 5건 | 1.7km | ✅ |
| 명량 | 전남 | 4건 | 2.0km | ✅ |
| 서부전선 | 경기 | 4건 | 4.0km | ✅ |
| 한산: 용의 출현 | 경남 | 4건 | 7.3km | ✅ |
| 지슬 | 제주 | 4건 | 14.0km | ✅ |
| 노량: 죽음의 바다 | 경남 | 3건 | **50.3km** | ⚠️ 경계 (통영 충렬사 ↔ 남해 관음포) |
| 안시성 | 경기/서울/충북/강원 | 각 1~2건 | — | ❌ 4개 시도로 쪼개짐 |
| 태극기 휘날리며 | 대구/서울/경북 | 각 1건 | — | ❌ |
| 나머지 17개 조합 | | 1~2건 | — | ❌ 앵커 부족 |

**가장 아픈 건 「안시성」** 이다. 후보 12건으로 제일 많은데 4개 시도에 흩어져 있어서 **하루 코스가 하나도 안 나온다.**

**이 결정이 만드는 숙제 2개**

1. **`TimelineEstimator`의 이동 속도 25km/h는 도심 기준이다.** 차로 다니는 하루 여행이면 시외 구간은 60~80km/h다. 지금 값으로 계산하면 「인천」(21km)만 해도 이동에 50분이 잡힌다. → **논의 3**
2. **`allowance` 기본 3km / 최대 20km도 도보~단거리 기준이다.** 차량이면 식당·카페 후보 반경이 달라져야 한다. → **논의 3**

## 3. 결정 4개를 전부 적용하면

```
콘텐츠 23편
   │  ① 시대 범위 (~1960)          →  20편   (-3편)
   │  ② 앵커 발견 + 검수            →  장소 후보 63건
   │     (여행코스 5건·시대밖 7건 제외)
   │  ③ 작품 × 지역으로 분할         →  27개 조합
   │  ④ 앵커≥3 & 60km 이내          →  하루 코스 8개  ← 실제로 서비스 가능한 것
   ▼
   나머지 19개 조합 = 앵커 1~2곳  →  논의 4에서 처리 방법 결정 필요
```

**즉 지금 데이터로 제대로 된 하루 코스가 나오는 건 8개다.** 검수를 하면 오매칭이 빠져서 더 줄 수 있다.

## 4. 결정에서 새로 생긴 질문 — 의견 주세요

### 논의 1 — `relation_type`(역사현장/촬영지/일반명소)을 누가 매기나 ★ 결정 2에서 파생

위에서 본 대로 **이름 문자열로는 자동 분류가 안 된다.**

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| ⓐ | **검수자가 CSV에서 손으로** (`relation_type` 열 추가) | 정확. 어차피 검수는 해야 함 | 63건 × 판단 1회 추가 |
| ⓑ | **cat3를 CSV에 담고 코드로 매핑** (`A02010700` 유적지 → 역사현장, `A02030400` 이색체험 → 촬영지 후보) | 자동화. 스크립트에 컬럼 하나 추가하면 됨 | cat3가 실제로 잘 갈리는지 미검증. 설계문서에 *"cat3로 촬영지를 거를 수 없다"* 는 실측 기록이 있음 |
| ⓒ | **LLM이 이름+줄거리 보고 판정** | 「제승당」이 이순신 유적인 걸 안다 | 환각. 다만 3지 선택이라 위험은 낮은 편 |

**제 의견:** ⓑ를 먼저 시도해보고(스크립트 1줄), 안 갈리면 ⓐ로 갑니다. 어차피 검수는 하니까요.

---

### 논의 2 — "지역"의 단위를 뭘로 잡나 ★ 결정 4에서 파생

위 표는 **시도(市道)** 로 묶은 결과인데, 이게 최선인지 모르겠습니다.

| 선택지 | 내용 | 「안시성」에 적용하면 |
| --- | --- | --- |
| ⓐ | **시도** | 4개로 쪼개짐 → 전부 앵커 부족 → 코스 0개 |
| ⓑ | **차량 60분 반경으로 클러스터링** | 아차산성+고구려대장간마을(서울/경기 경계, 0.6km)이 **같은 묶음**이 됨 → 코스가 생길 수 있음 |
| ⓒ | 사용자가 지역을 먼저 고름 | 단순하지만 진입 단계가 늘어남 |

**제 의견:** ⓑ가 맞다고 봅니다. 시도 경계는 행정구역일 뿐이고, 아차산성(서울)과 고구려대장간마을(경기 구리)은 **600m 거리**인데 ⓐ로는 다른 코스가 됩니다.

---

### 논의 3 — 차량 기준 상수값을 얼마로 ★ 결정 4에서 파생

| 값 | 현재 | 근거 | 제안 |
| --- | --- | --- | --- |
| 이동 속도 | 25 km/h | 도심 혼잡 기준 | 40~60 km/h? |
| 허용 우회거리 기본 | 3 km | 도보 기준 | 10 km? |
| 허용 우회거리 최대 | 20 km | | 30 km? |
| 체류 시간 | 120/90/60분 | *"팀 합의 후 재조정 가능"* (설정 주석) | 유지? |
| 하루 시작 | 10:00 | | 유지? |

숫자는 감으로 정할 수밖에 없어서, **실제 코스 8개를 뽑아보고 타임라인이 말이 되는지 보고 정하는 게** 낫다고 봅니다.

### 논의 4 — 앵커 1~2곳인 조합 19개를 어떻게 할까

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| ⓐ | **숨김** (앵커 3곳 미만 제외) | 품질 보장 | 20편 중 보여줄 게 8개 코스뿐 |
| ⓑ | **보여주되 문구를 낮춤** — "반나절 코스" / "이 작품 분위기의 코스" | 커버리지 유지. 거짓말 안 함 | 기대에 못 미침 |
| ⓒ | **같은 시대·인근 지역 앵커로 채움** | 항상 3곳 | 작품 관련성 희석 |

---

### 논의 5 — 검수 비용을 어떻게 감당하나

**A등급 0건 / B등급 75건.** 자동 통과가 하나도 없어서 전부 사람이 봐야 합니다. 20편에 63건이면, 100편이면 **300건 이상**입니다.

| 선택지 | 내용 | 단점 |
| --- | --- | --- |
| ⓐ | 전수 수동 | 확장 불가 |
| ⓑ | 자동 승인 규칙 확대 (검색어가 장소명에 완전 포함 + 좌표 + 이미지) | 「무사」→충무사 같은 오매칭이 통과할 위험 |
| ⓒ | **LLM 1차 + 사람 샘플** | LLM 비용. 샘플 비율 합의 필요 |

### 논의 6 — `content_place` 스키마 (박세현 님 확인 필요)

결정 2를 구현하려면 `relation_type`이 필요한데, `ContentPlace`는 박세현 님 소유 엔티티라 못 건드리고 있습니다.

```java
ContentPlace {
    content_id
    external_content_id
    relation_type    // ★ HISTORICAL | FILMING | GENERAL  ← 결정 2 구현에 필요
    grade            // A | B | C
    evidence         // 근거
    recommend_order
}
```

**컬럼 추가가 가능한지, 아니면 별도 테이블로 뺄지** 알려주시면 그에 맞춰 짜겠습니다.

## 7. 지금 막혀 있는 것

**검수 63건만 끝나면 추천/루트 404가 전부 풀립니다.** 코드는 다 돼 있습니다.
