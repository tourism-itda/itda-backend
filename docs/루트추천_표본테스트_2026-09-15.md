# 새 콘텐츠 루트 추천 표본 테스트 — 2026-09-15

## 요약

- 운영 DB 수정 없이 공개 API, 새 dev의 HistoricalPlaceData, 카카오 REST API로 실험했다.
- 이번 목록 스냅샷은 93편이다. 앞선 조회의 100편과 다르며 변경 원인은 확인하지 않았다.
- 신규 후보 작품 `나는 왕이로소이다`(138713), `풍운의 궁전`(458343)은 이번 공개 목록에도 존재한다.
- 작품 요약과 dev의 세종→경복궁/세종대왕릉 매핑을 사용해 관련 명소 후보를 수동 지정했다. 작품의 실제 장면·촬영지 관계를 승인한 결과가 아니다.
- 일반 명소 후보는 한국관광공사 자료에서 선택하고 카카오 검색으로 좌표를 조회했다. 자동 거리순 추천과 비교하기 위한 수동 후보 보강이다.
- 서비스 RoutePlanner를 수정하거나 운영 추천 API에 연결하지 않았다. 별도 GET-only 실험 스크립트다.

## 데이터 조회의 한계

- 공개 콘텐츠 93편, 인물 95명 조회.
- 인물별 작품/장소 GET 총 190회 중 128회 오류: HTTP 502 32회, HTTP 상태 없는 네트워크 오류 96회.
- 성공한 조회만으로 공개 작품의 인물 연결을 확인하지 못했다. 이를 DB에 연결 0건이라고 해석하면 안 된다.
- 해당 서버의 응답 지연 때문에 전수 관계 검증을 끝내지 못했다. 실패한 작품은 미검증 상태로 남긴다.
- 상세 GET은 누락 ID에 대해 콘텐츠 수집을 트리거할 수 있어 호출하지 않았다. 운영 쓰기/수집 트리거를 실행하지 않았다.

- 최종 세 가지 유효 조합(서울 WALK/CAR, 여주 CAR)의 각 두 구간에서 식당·카페 타원 후보를 찾았다. 각 종류당 첫 페이지 15건이 타원을 통과했다. 전체 업체 수나 전수 검색 결과가 아니다.
- 타원은 직선 우회량 기준이며 각각 300m(WALK), 3,000m(CAR)를 사용했다. 선택 후 실제 식당·카페를 경유한 전체 동선은 아직 검증하지 않았다.
- 상촌재 등은 운영일/시간 확인이 필요하다. 테스트 당일 즉시 방문 가능한 완성 일정이나 사실관계 검수 완료 코스로 표시하지 말 것.

## 발견한 문제와 수정 방향

1. 관광명소 카테고리의 가까운 순 결과만 사용하면 관광코스 자체, 이름만 있는 골짜기를 독립 명소로 선택한다. 관광 가치·장소 타입 필터가 거리 점수보다 먼저 필요하다.
2. 키워드 검색 첫 결과를 그대로 쓰면 세종대왕유적관리소, 영월공원 주차장이 관광지로 섞인다. 본 장소와 시설/관리사무소/입구/주차장을 구분해야 한다. 마지막 표본에서는 관리·운영/주차장 카테고리를 제외했다.
3. dev HistoricalPlaceData의 세종대왕릉 좌표 (37.2647,127.6086)는 카카오의 `영녕릉 세종대왕유적지구 세종대왕릉` (37.3080664564253,127.602939250485)과 약 4,848m 다르다. DB/원본 코드는 아직 수정하지 않았다. 거리 추천 전에 원본 장소 좌표 정합성 검증이 필요하다.
4. 첫 실험은 잘못된 세종대왕릉 좌표 주변의 골짜기 둘을 연결했고 경로 API가 성공했다. HTTP 200과 짧은 거리가 올바른 관광 추천을 보장하지 않는다.
5. 공개 목록에는 기존 시대 범위와 맞지 않을 수 있는 작품도 있다. 범위 필터·관련성 검수와 경로 생성은 구분해야 한다.

## 추천 구현 제안

1. 콘텐츠 관련 명소를 배치로 발굴·검수한다. 작품 관련 명소가 확인 결과 0건인 경우만 기록하고 숨긴다. 외부 API 실패는 0건으로 확정하지 않는다.
2. 검수한 일반 관광지 목록을 지역별로 확보한다. 장소 API는 좌표/업체 확인에 사용하고 작품 관련성과 관광 가치를 대신 판단하게 하지 않는다.
3. DB 좌표로 거리·영업시간·장소 유형·중복을 먼저 거른다. 여행지 3곳은 관련 1~2 + 일반 1~2로 구성한다.
4. 코드로 순서 후보를 좁히고 최종 두 구간만 길찾기 API로 검증한다. 실패 시 다음 후보를 제한된 횟수만 시도한다. 자동차는 방향별 경로가 다르므로 A→B와 B→A를 별개로 취급한다.
5. 동일한 콘텐츠·지역·이동수단·데이터 버전의 추천 결과는 재사용한다. 원본 경로 데이터 저장 기간과 사용 범위는 공급자 정책을 확인한 뒤 정한다. 실패 응답을 '경로 없음'으로 장기 캐시하지 않는다.
6. 사용자에게 필요한 구간만 식당·카페 후보를 조회한다. 드래그 중 매 프레임 호출하지 말고 요청 중복 방지와 디바운스를 적용한다.
7. 식당·카페 선택을 확정한 뒤 전체 경유 경로를 검증한다. 개별 타원 조건만으로 총 보행 예산을 보장하지 않는다.
8. API별 호출 카운터·하루 예산·동시성 제한·429 처리와 캐시 사용 상태를 기록한다. 재시도도 호출 예산에 포함한다.

예산 계산 예: 작품 100편 × 모드당 코스 1개 × 두 구간 = 도보 200회 + 자동차 200회 (첫 조합 성공 가정). 세 가지 순서를 모두 외부 검증하면 모드별 최대 600회가 될 수 있다. 도보 1,000회 한도에서 모든 후보를 전수 호출하는 방법은 여유가 작다.

캐시 없이 신규 도보 코스 생성만 2회/건이면 이론상 500건/일에 한도에 도달한다. 식당·카페 경유 검증·재시도·다른 사용량을 포함하면 더 적다. 따라서 '사용자 500명까지 안전'으로 해석하면 안 된다.

## 재현 자료

- `scripts/route-data-probe.py`: 콘텐츠·인물·장소 연결 읽기 전용 조회.
- `scripts/route-sample-probe.py`: 표본 카카오 호출, 종류별 호출 상한, 실행 내 중복 요청 캐시. 키는 표준입력으로만 받는다.
- `build/route-probe/inventory.json`: 이번 목록과 조회 오류 스냅샷.
- `build/route-probe/baseline-results.json`: 최초 거리순 결과.
- `build/route-probe/curated-first-results.json`: 후보 보강 1차 결과.
- `build/route-probe/sample-results.json`, `resolved-samples.json`, `samples.json`: 최종 결과와 입력. build는 Git 미추적이다.
- 키는 코드/문서/결과 파일에 저장하지 않았다.
