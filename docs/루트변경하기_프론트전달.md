# "루트 변경하기" 프론트 연동 — 2026-09-17

> 백엔드는 구현돼 있습니다. 프론트가 보낼 것은 **필드 하나**(`exclude_place_ids`)뿐입니다.
> 다만 **누적해서 보내야** 하고, 이번에 서버에서 고친 것이 두 개 있어 같이 적었습니다.

## 1. 보낼 것

같은 엔드포인트를 다시 부르면 됩니다. 새 API 없습니다.

```jsonc
POST /api/itineraries/route
{
  "content_id": 133200,

  // 사용자가 촬영지를 골랐으면 그대로 유지해서 보냅니다 (안 골랐으면 생략)
  "spot_place_ids": [30],

  // 지금까지 본 루트의 place_id 를 전부 누적해서 보냅니다
  "exclude_place_ids": [30, 122, 29, 225, 31, 226],

  "allowance_meters": 3000        // 슬라이더 값. 생략하면 3000
}
```

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `content_id` | 예 | 작품 id |
| `spot_place_ids` | 아니오 | 사용자가 "꼭 가고 싶다"고 고른 촬영지. **비우면 서버가 전부 고릅니다** |
| `exclude_place_ids` | 아니오 | 이번엔 빼고 싶은 place_id. **"루트 변경하기"의 전부입니다** |
| `allowance_meters` | 아니오 | 동선 허용거리(m). 기본 3000, 최대 20000 |

응답 형식은 첫 호출과 **완전히 동일**합니다. 화면을 그대로 다시 그리면 됩니다.

## 2. 프론트가 관리할 상태는 하나

```
excludedIds: number[]   // 지금까지 본 모든 루트의 place_id 를 누적
```

```js
// 최초 루트 생성
const first = await postRoute({ content_id, spot_place_ids: picked });
excludedIds = placeIdsOf(first);

// "루트 변경하기" 누를 때마다
const next = await postRoute({
  content_id,
  spot_place_ids: picked,          // 사용자 선택은 계속 같이 보냄
  exclude_place_ids: excludedIds,  // 누적된 것 전부
});
excludedIds = [...new Set([...excludedIds, ...placeIdsOf(next)])];

function placeIdsOf(route) {
  return route.slots.filter(s => s.place).map(s => s.place.place_id);
}
```

> ⚠️ **누적이 핵심입니다.** 직전 루트 것만 보내면 A ↔ B 로 왔다갔다 합니다.
> 식당·카페 슬롯은 처음엔 비어 있으므로 `s.place` 가 있는 칸만 모으면 됩니다.

## 3. 이번에 고친 것 두 가지 (프론트 동작에 영향)

### 3-1. 고른 촬영지가 사라지던 문제

지금까지는 `spot_place_ids` 로 고른 곳이 `exclude_place_ids` 에도 들어 있으면 **고른 곳이 루트에서
빠졌습니다.** 위 2장처럼 누적해 보내면 반드시 겹치므로 항상 터지는 조합이었습니다.

운영에서 재현한 것:

```
광해 — 창덕궁(30)을 고르고 "변경하기"
  보낸 것: spot_place_ids=[30], exclude_place_ids=[30,122,29]
  받은 것: 조계사(서울) / 종묘(31)[SCORED] / 서울 동대문 닭한마리 골목
           → 고른 창덕궁이 없다
```

**이제 서버가 제외 목록에서 `spot_place_ids` 를 걸러 냅니다.** 프론트는 직전 루트를 통째로
제외에 넣어도 안전합니다 — 굳이 고른 것만 빼서 보낼 필요 없습니다.

### 3-2. 1곳만 골라도 관련 명소가 2곳 들어가던 문제

앵커가 2곳 이상인 작품에서 사용자가 **1곳만 골라도 서버가 나머지 1곳을 자동으로 끼워 넣었습니다.**

```
덕혜옹주 — 덕수궁(162) 한 곳만 고름
  전: 덕수궁[USER] / 정동구 여행 센터[GENERAL] / 창덕궁 낙선재[SCORED]  ← 안 고른 앵커가 들어옴
  후: 덕수궁[USER] / 일반명소 / 일반명소
```

**이제 고른 개수를 그대로 지킵니다.** 1곳을 고르면 관련 1 + 일반 2, 2곳을 고르면 관련 2 + 일반 1,
아무것도 안 고르면 기존처럼 자동추천입니다.

`filled_by` 로 구분하시면 됩니다:

| `filled_by` | 뜻 |
| --- | --- |
| `USER` | 사용자가 고른 촬영지 |
| `CURATED` | 서버(Claude)가 고른 관련 명소. `reason` 문구가 같이 옵니다 |
| `SCORED` | 서버가 점수로 고른 관련 명소 |
| `GENERAL` | 주변 일반 관광명소. **작품 관련 문구를 붙이면 안 됩니다** |

## 4. 몇 번이나 누를 수 있나

작품마다 다릅니다. 앵커 수가 결정합니다.

| 앵커 수 | 작품 수 | 변경하기를 누르면 |
| ---: | ---: | --- |
| 3~4곳 | 20편 | **관련 명소까지** 바뀝니다 |
| 1~2곳 | 28편 | 관련 명소는 유지되고 **일반 명소만** 바뀝니다 |

앵커 1곳인 작품이 가장 많습니다(26편 중 20편). 그런 작품은 관련 명소가 고정이고 일반 명소 2곳만
돌아가는 게 정상입니다.

**후보가 고갈되면 서버가 제외를 무시하고 이전 조합을 다시 줍니다.** 명소가 3곳보다 적어지는 일은
없습니다. 응답이 직전과 같으면 "더 볼 코스가 없습니다" 정도로 안내하시면 됩니다. 프론트에서
직전 응답과 place_id 집합을 비교하면 판정할 수 있습니다.

## 5. 주의

- **식당·카페 슬롯은 재생성해도 계속 비어 있습니다.** 그 칸은 사용자가 구간 후보에서 직접 고르는
  설계라 서버가 채우지 않습니다. 이미 고른 식당이 있으면 **프론트가 들고 있다가 다시 붙여야 합니다** —
  루트 재생성 응답에는 담기지 않습니다.
- 재생성하면 촬영지가 바뀌므로 **이미 고른 식당·카페의 동선이 안 맞을 수 있습니다.** 관련 명소가
  바뀌는 작품(앵커 3~4곳)에서는 식당 선택을 초기화하는 편이 자연스럽습니다.
- `anchor_source` 가 `PERSON_CHAIN` 이면 촬영지가 아니라 **작품 속 인물과 연결된 곳**입니다.
